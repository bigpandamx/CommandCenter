# Aegis Desktop ↔ Command Center Sync Protocol (v1)

## Purpose

Aegis desktop installs are meant to stay lean and flexible. State that's
expensive, sensitive, or needs cross-org visibility -- license entitlements,
release manifests, threat intel, fleet telemetry -- lives in Command Center
instead. This document specifies the wire protocol a desktop install uses to
enroll and stay in sync with Command Center.

Status: **enroll**, **check-in**, and **telemetry upload** are implemented
and unit-tested (`Customer-Connections/Desktop-Apps/src`). Threat-intel
delta sync is specified below but not yet implemented -- see "Not yet
built" at the end.

## Identity model

- Every device belongs to exactly one **Organization** (tenant).
- A device is enrolled using a short-lived, single-use (by default)
  **enrollment token**, generated by an org admin inside Command Center and
  handed to whoever is installing Aegis (e.g. embedded in an installer
  config, or typed in during first run).
- Enrollment exchanges the token for a **device API key** the desktop app
  must then store locally (OS keychain, not plaintext config) and send as a
  Bearer token on every subsequent request. Command Center stores only a
  salted hash of this key -- it cannot be recovered or re-displayed. A lost
  key means the device must be re-enrolled.
- Re-running enrollment for the same organization + machine fingerprint
  rotates the key on the existing device record rather than creating a
  duplicate device (handles reinstalls without orphaning history).

## Transport

- HTTPS, JSON bodies, `Content-Type: application/json`.
- Base path: `/v1`.
- Auth: `Authorization: Bearer <device_api_key>` on every endpoint except
  `/v1/enroll` (which authenticates via the enrollment token in the body
  instead, since the device doesn't have a key yet).

## Endpoints

### `POST /v1/enroll`

Request:
```json
{
  "token": "the enrollment token",
  "fingerprint": "stable per-machine identifier",
  "displayName": "human-readable device name",
  "platform": "windows | macos | linux",
  "appVersion": "2.4.0"
}
```

Response `201`:
```json
{
  "deviceId": "uuid",
  "apiKey": "dk_xxxxxxxx_...",
  "organizationId": "uuid",
  "organizationName": "Acme Corp",
  "channel": "stable | beta | canary"
}
```
`apiKey` is returned exactly once. The client must persist it before doing
anything else with the response. `organizationName` lets a caller
provisioning a brand-new local tenant from this token skip a second
round-trip just to learn what to call it.

Errors: `401 invalid_token`, `401 token_expired`, `409 token_exhausted`,
`404 org_not_found`.

### `POST /v1/checkin`

Sent on a timer (see `nextCheckinSeconds` in the response; default 15
minutes, halved when there's pending work so the client acts sooner without
Command Center needing to push anything).

Request:
```json
{
  "deviceId": "uuid",
  "appVersion": "2.4.0",
  "health": {
    "uptimeSeconds": 3600,
    "lastErrorCode": null
  }
}
```

Response `200`:
```json
{
  "serverTime": "2026-07-20T12:00:00.000Z",
  "updateAvailable": true,
  "latestVersion": "2.5.0",
  "commands": [
    { "id": "uuid", "type": "resync_config", "issuedAt": "..." }
  ],
  "nextCheckinSeconds": 450
}
```

Errors: `401 unauthorized` (bad/mismatched key), `404 device_not_found`,
`403 device_revoked`.

Deliberately kept small: `health` is a coarse snapshot, not a telemetry
dump. Bulk telemetry goes through its own endpoint (below) so a slow
telemetry pipeline never blocks the update/command check.

### `POST /v1/telemetry`

Batched upload of ConMon evidence, usage metrics, error reports, and
coarse health snapshots. Separate from check-in's `health` field on
purpose -- check-in stays small and frequent; telemetry can be larger and
less time-sensitive.

Request:
```json
{
  "deviceId": "uuid",
  "events": [
    {
      "type": "conmon_report | usage_metric | error_report | health_snapshot",
      "occurredAt": "2026-07-20T11:58:00.000Z",
      "payload": { "...": "event-type-specific JSON, max 32KB per event" }
    }
  ]
}
```

Response `202`:
```json
{ "accepted": 2, "receivedAt": "2026-07-20T12:00:00.000Z" }
```

Batch limits: 1–500 events per request, each event's `occurredAt` must be
within 30 days in the past and 5 minutes of clock skew into the future.
Errors: `401 unauthorized`, `404 device_not_found`, `403 device_revoked`,
`400 empty_batch` / `invalid_event`, `413 batch_too_large`.

Command Center admins can view an org's recent telemetry via
`GET /v1/admin/organizations/:organizationId/telemetry` (optional `since`
and `limit` query params) -- requires the `org:read` permission.

## Not yet built (specified, not implemented)

- `GET /v1/threat-intel/feed?since=<cursor>` -- delta sync of CVEs/advisories
  relevant to the org's tracked products.
- `POST /v1/license/validate` -- currently folded implicitly into
  enroll/check-in (an inactive or over-quota org will simply fail to
  enroll new devices once entitlement enforcement is added to
  `enrollDevice`); a standalone endpoint may be needed once entitlements
  get more granular than "trial/standard/enterprise".
- Command *acknowledgement* -- `clearPendingCommands` exists on the
  repository port but nothing calls it yet. A device currently sees the
  same pending commands on every check-in until Command Center's operator
  UI marks them delivered; the client-side apply-and-ack flow needs to be
  designed together with whoever builds the Aegis-side client.
- Telemetry retention/pruning -- `telemetry_events` grows without bound;
  no scheduled job exists yet to prune old rows (see the migration's
  comment on this).
