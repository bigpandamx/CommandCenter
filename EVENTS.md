# Events

Command Center as the event bus hub: a durable, append-only, idempotent
event log any service-account-authenticated caller can publish to and
poll from. See `Platform-Services/Events/` for the implementation.

**This is deliberately not a message broker.** It's the lightest thing
that could work for the number of services that actually exist today
(Aegis publishes; Command Center itself is the first subscriber, via
staff tooling reading the log directly). It's shaped to scale cleanly to
a handful more services without a rewrite -- not to replace
Kafka/RabbitMQ/SNS-SQS if this product ever needs that kind of throughput
or fan-out. If that day comes, this module's job is done, not this
module itself; a real broker would take over event *distribution* while
keeping the same envelope contract below.

## Why HTTP + polling, not push/webhooks

Every other integration point in this system already uses direct HTTP +
graceful degradation (org enrollment, checkin, telemetry, the support
panels). This follows the same shape rather than inventing a new
delivery mechanism: publishers write events via `POST /v1/service/events`
(service-account authenticated, same credential type as everything else
Aegis calls); subscribers read them via `GET /v1/service/events`, cursor
by `afterSequence`. No new auth to build, no webhook delivery/retry
infrastructure on Command Center's side (that complexity, if a publisher
needs guaranteed delivery despite Command Center being unreachable,
lives on the *publisher's* side as a local outbox -- see Aegis's
`app/services/event_outbox_service.py` for the reference
implementation).

## The envelope

```json
{
  "eventId": "a stable UUID the publisher generates before ever sending this event",
  "type": "organization.activated",
  "source": "aegis",
  "occurredAt": "2026-07-24T12:00:00.000Z",
  "payload": { "...": "event-type-specific" }
}
```

- **`eventId`** -- generated by the publisher, not Command Center. This
  is what makes `POST /v1/service/events` idempotent: if a publisher's
  outbox retries a delivery whose response was lost to a network blip
  (the event was actually recorded, the *acknowledgment* wasn't), the
  retry carries the same `eventId` and is treated as a no-op rather than
  creating a duplicate. Generate it once, when the event is created
  locally -- not fresh on every delivery attempt.
- **`type`** -- dot-namespaced, lowercase, past-tense:
  `<concept>.<what_happened>`. Namespace by the concept the event is
  about (`organization`, `billing`, `agent`), not by which service
  published it -- `source` already carries that. Not a compile-time
  enum; Command Center accepts any well-formed type string, so a new
  event type never requires a Command Center code change to start
  flowing. `Platform-Services/Events/src/eventService.ts` enforces the
  format, not a fixed vocabulary.
- **`source`** -- which system published this (`"aegis"`,
  `"command_center"`). Free text today; if more publishers show up,
  this is the field that tells them apart.
- **`occurredAt`** -- when the publisher says this happened. Can be
  earlier than when Command Center actually received it (a retried or
  delayed delivery). Not the pagination cursor -- see below.
- **`payload`** -- event-type-specific JSON. No schema enforced at this
  layer; that's each event type's own contract between whoever
  publishes it and whoever consumes it, documented wherever that event
  type is introduced (see "Events in use" below).

## Cursor-based polling: `sequence`, not a timestamp

The list endpoint pages by `afterSequence` (a strictly monotonic,
database-assigned integer), not by `occurredAt` or `receivedAt`. This
was a real bug caught during development, not a hypothetical one: two
events published back-to-back can receive the *same* millisecond
timestamp (JS `Date` resolution, or even two sufficiently fast
concurrent Postgres inserts), and a cursor built on a value that can tie
will silently drop an event from a subscriber's "everything since my
last cursor" query -- forever, with no error, no way to notice short of
an independent audit. `sequence` (`BIGSERIAL`) can't tie. Any future
event-consuming code should page by `sequence`, never by a timestamp
field, however tempting a human-readable cursor might seem.

## Reliability: outbox on the publisher's side, not delivery guarantees on the hub's side

Command Center doesn't push events to subscribers or retry failed
deliveries -- it just durably records what's published and lets
polling readers ask for what they've missed. If a *publisher* needs
"this event eventually gets published even if Command Center is down
right now," that's the publisher's own responsibility, via a local
outbox: write the event to a local table first, attempt delivery,
retry on failure until it succeeds. See Aegis's
`app/models/outbox_event.py` / `app/services/event_outbox_service.py`
for the reference implementation, and
`app/services/command_center_scheduler.py`'s existing pattern for how
it's driven on a schedule.

## Events in use

- **`organization.activated`** -- published by Aegis after
  `activate_organization_from_enrollment_token` succeeds. `payload`:
  `{"aegisOrganizationId": number, "commandCenterOrgId": string}`.
  Purely additive/informational today -- Command Center already learns
  about the same activation synchronously via the enrollment token
  redemption itself; this is a durable, independently-queryable record
  of it, and the first real event proving the envelope/outbox pattern
  end to end for whatever gets added next.

Add new event types to this list when you introduce them, with their
payload shape -- this section is the source of truth a future consumer
needs to read before writing a subscriber, so it should never fall out
of date with what's actually being published.
